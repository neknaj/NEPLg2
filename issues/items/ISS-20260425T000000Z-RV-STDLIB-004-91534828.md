# RV-STDLIB-004: collection free が要素の Drop を呼ばない

旧 `doc/review20260425` から移行した Issue。新しい正の ID は `ISS-20260425T000000Z-RV-STDLIB-004-91534828`。

## 要約

`Vec<str>` や `Vec<Owned>` のような要素がさらに所有権を持つ場合、collection の `free` は要素ごとの drop を呼びません。逆に shallow copy と組み合わさると double free も起こり得ます。

## 影響

stdlib の collection を使うほど、要素所有権のリークまたは二重解放が増えます。Resource IR がない現行 compiler では型システムでも補足しきれません。

## 修正方針

collection は `Drop<T>` bound を持つ要素 cleanup と、単純 dealloc の fast path を分けます。最低限、owning element を含む collection は `free` の仕様で責務を明確にし、compiler drop pass と整合させます。

## 検証

drop counter を持つテスト用型を作り、`Vec<T>` / `List<T>` / `HashMap<K,V>` の free で要素 drop 回数が一致することを確認します。

## 2026-04-28 issue 整理

この issue は Stage 6 の collection API / element cleanup issue とする。`free` に要素 drop loop を足すだけでは完了としない。`Copy` read、borrowed read、owned remove/pop、container drop、storage-only dealloc を API と型制約で分け、compiler 側の `InitializedCell` / drop obligation と整合させる。

storage owner と initialized cell の compiler 境界は `ISS-20260427T164432612Z-CORE-MEM-DEALLOC-APIS-DO-NOT-ENCODE--204F1F47`、`MemPtr` と owner token の分離は `ISS-20260427T152958303Z-MEMPTR-AND-REGIONTOKEN-LACK-COMPILER-0BC8ECDF` に分ける。

## 2026-04-27 全体レビュー追記

`stdlib/` 全体を raw memory / collection ownership 目線で再確認した結果、この issue は引き続き open のまま扱うべきです。`Vec<T>` / `Stack<T>` / `RingBuffer<T>` / `BinaryHeap<T>` / `HashMap<K,V>` / `HashSet<T>` / `List<T>` などは、内部 storage を `dealloc_raw` または `MemPtr` 経由で解放する fast path が中心で、要素 `T` / 値 `V` の Drop 契約を型で表現していません。

特に `Vec<T>` の `get(Vec<T>, i32) -> Option<T>` や各 collection の by-value observation API は、所有 handle を消費する一方で内部 buffer 側の要素所有権を明確に減らさないため、`T` が owning type になった時の leak / shallow move の判断が caller と raw memory helper に漏れます。修正時は単に `free` を増やすのではなく、`Copy` read、borrowed read、owned remove/pop、container drop を API と型制約で分ける必要があります。

関連して、single-cell owner である `SelfhostOutcome` の cleanup 問題は collection ではないため `ISS-20260427T132414663Z-SELFHOSTOUTCOME-FREE-DROPS-ONLY-STOR-CFD7EA86` に分離しました。

## 2026-04-28 compiler / mem 責務分割レビュー追記

collection 側の問題は、単に `free` 内で loop して要素 drop を呼ぶだけでは完了しない。`stdlib/core/traits/copy.nepl:151` 以降で `MemPtr<T>` は Copy な non-owning address と説明されている一方、`stdlib/alloc/collections/vec.nepl:127`、`stack.nepl:116`、`binary_heap.nepl:41` などでは `MemPtr` が storage owner の実体としても使われている。このため collection API は「storage owner」「borrowed pointer」「owned element move」「copy read」を型で分けられていない。

この issue の修正では、`ISS-20260427T152958303Z-MEMPTR-AND-REGIONTOKEN-LACK-COMPILER-0BC8ECDF` の owner/provenance 設計と同期し、要素 cleanup、storage dealloc、borrowed observation、owned remove/pop を分けてから実装する必要がある。stdlib 側だけで場当たり的に drop 呼び出しを増やすと、compiler 側 Resource IR 導入後に double drop または leak の責務が再び曖昧になる。

追加レビューで、collection 固有ではない `core/mem` の dealloc 契約不足を `ISS-20260427T164432612Z-CORE-MEM-DEALLOC-APIS-DO-NOT-ENCODE--204F1F47` に分離した。この issue は collection API と要素 cleanup の設計を扱い、storage owner / initialized cell / dealloc obligation の型・compiler 境界は同 issue と同期して修正する。
