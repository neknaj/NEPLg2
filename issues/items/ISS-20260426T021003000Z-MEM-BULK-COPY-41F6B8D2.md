# ISS-20260426T021003000Z-MEM-BULK-COPY-41F6B8D2: stdlib byte copy paths use byte-by-byte loops instead of bulk memory copy

## 概要

stdlib の raw memory copy は `load_u8` / `store_u8` の byte loop に偏っている。
`stdlib/core/mem.nepl` には `memory.copy` などで効率を上げる TODO があり、`realloc_raw`、`io_bytebuf_from_str`、`io_bytebuf_to_str`、string copy 系 API が同じ制約を受ける。

## 根拠

- `stdlib/core/mem.nepl:20` に `memory.copy` 活用 TODO がある。
- `mem.nepl:409` の `realloc_raw` は `copy_bytes` 分を 1 byte ずつ copy する。
- `stdlib/alloc/io.nepl:86` と `:107` は `ByteBuf` / `str` 変換で 1 byte ずつ copy する。
- `stdlib/alloc/string.nepl` の `concat` / `sb_build` / `str_slice` も byte loop で copy する。

## 問題

self-host compiler は source text、diagnostic message、WASM binary、module path、serialized output で大量の連続 byte copy を行う。
byte loop だけだと copy 自体の計算量は O(n) でも定数倍が大きく、Vec grow や StringBuilder build のたびに実行時間が増える。

## 影響

WASM emitter の binary section build、source file read、diagnostic rendering が大きくなるほど CPU 時間が増える。
bulk copy がない状態で ByteBuilder を実装すると、builder 自体は growable でも append の実コストが不要に高いまま残る。

## 修正方針

`mem_copy` / `mem_move` / typed slice copy API を stdlib public API として追加し、WASM backend では `memory.copy`、LLVM backend では `llvm.memcpy` 相当へ下げる。
overlap を許す API と許さない API を分け、`realloc_raw`、`ByteBuf`、string copy、ByteBuilder から順に利用する。

## 検証

- overlap なし / overlap あり / zero length の memory copy doctest。
- `realloc_raw` と `ByteBuf` conversion が byte列一致を保つ regression。
- 大きな byte buffer copy の focused benchmark fixture。
