# ISS-20260426T021001000Z-BTREE-ARRAY-COST-B37E2A91: BTreeMap and BTreeSet are sorted arrays with O(n) updates

## 概要

`BTreeMap` / `BTreeSet` という名前だが、内部表現は B-tree ではなく、整列済み配列である。
検索は `lower_bound` で O(log n) だが、挿入と削除は要素 shift により O(n) になる。

## 根拠

- `stdlib/alloc/collections/btreemap.nepl:9` は内部表現が整列済み key/value 配列であると明記している。
- `btreemap.nepl:13` は本物の B-tree ではないと明記している。
- `btreemap.nepl:233` の `insert` は挿入位置以降の key/value を後ろへ shift する。
- `btreemap.nepl:282` の `remove` は削除位置以降の key/value を前へ shift する。
- `btreeset.nepl` も同じ構造で、`insert` / `remove` が shift する。

## 問題

self-host compiler では ordered map / set を scope、diagnostic、source span、module traversal、stable output order に使いたくなる。
現在の実装を大きな table に使うと、incremental insert / remove が O(n^2) の構築コストになりやすい。

## 影響

安定順序が必要な場所で `BTreeMap` を選ぶと、ファイル数・symbol 数・diagnostic 数に対して compile time と memory copy が急増する。
名前と実装のギャップにより、実装者が B-tree 相当の更新性能を期待して選ぶ危険もある。

## 修正方針

短期的には `SortedArrayMap` / `SortedArraySet` 相当の性質を doc と API 名で明確にし、self-host 計画では大規模 mutable table に使わない規則を書く。
中期的には node split を持つ本物の B-tree へ置き換えるか、ordered output 用には `HashMap + sorted key list` など用途別構造を用意する。

## 対応

`BTreeMap` / `BTreeSet` の module comment に、互換名であり実体は sorted-array collection であること、大きな mutable table には使わないこと、安定順序が必要な大きい出力では `HashMap` / `HashSet` と最終段階の key 整列に分けることを明記した。
API 名として `sorted_array_map_*` / `sorted_array_set_*` alias を追加し、B-tree 相当の更新性能を期待しない用途であることを呼び出し側に残せるようにした。
`doc/neplg2/self_host_plan.md` の S3 方針にも同じ制約を入れ、scope / symbol / module / diagnostic の大規模 mutable table で誤用しない規則にした。
