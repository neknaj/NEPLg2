# RV-STDLIB-009: 巨大 stdlib ファイルが分割されていない

旧 `doc/review20260425` から移行した Issue。新しい正の ID は `ISS-20260425T000000Z-RV-STDLIB-009-01749CCF`。

## 要約

stdlib の主要 file が肥大化しています。API、内部 helper、target-specific raw body、doctest が同居しており、修正範囲の把握が難しくなっています。

## 影響

コンパイル性能にも影響します。loader が import file を丸ごと clone / merge する現状では、巨大 stdlib file はそのまま型検査候補数と clone 量を増やします。

## 修正方針

`math/i32`, `math/i64`, `math/f32`, `math/f64`、`string/parse`, `string/format`, `stdio/read`, `stdio/write` のように用途別 module へ分割します。public facade は既存 path 互換を保ちます。

## 検証

分割前後で public import path の doctest が同じ結果になることを確認します。

## 2026-04-28 再レビュー

`string.nepl` は再実装で安全性が上がったが、UTF-8、builder、numeric parse/format、split、float conversion が同居している。self-host では text/token/diagnostic から広く使われるため、機能単位で `alloc/string/*` へ分ける必要がある。

`stdlib/neplg2/cli/args.nepl` は 661 lines で既に parser state、enum、doctest、classifier が同居しており、S6 の driver/reporter 実装前に `args/types`, `args/parse`, `args/tests` 相当へ分ける候補として追跡する。

## 2026-04-29 対応メモ

`alloc/string.nepl` の byte scanner helper 群を `stdlib/alloc/string/scanner.nepl` へ分離した。後方互換のための wrapper facade は残さず、byte scanner を使う module が `alloc/string/scanner` を明示 import する設計にした。

この分割により、parser / scanner 向けの ASCII byte 分類、byte range find、line end / next line、inline space scan の loop 実装は `alloc/string/scanner` が所有する責務になった。`alloc/string.nepl` は UTF-8 slice / builder / numeric conversion など文字列本体の責務に寄せ、scanner helper は `scanner::str_find_byte_range` のように呼び出す。既存 facade を試した際に、同名 public API から `scanner::str_*` を呼ぶと resolver が D3001 にする問題も確認したため、compiler 側の問題は `ISS-20260429T041244376Z-FACADE-MODULE-CANNOT-DISAMBIGUATE-SA-7F898FA5` として分離した。

`stdlib/neplg2/core/module/import_spec.nepl`、`stdlib/nm/parser.nepl`、`stdlib/nm/html_gen.nepl` は scanner module を直接 import するように更新した。`nodesrc/test_stdlib_byte_scanner_helpers_boundary.js` も更新し、scanner 実装本体が `alloc/string/scanner.nepl` にあり、`alloc/string.nepl` に scanner facade が戻らないことを固定した。

この issue はまだ open のまま扱う。`alloc/string` には UTF-8 slice、StringBuilder、numeric parse/format、split が残っており、`core/math`、`std/streamio`、`std/fs`、`stdio`、`nm/parser` など他の巨大 file も未分割である。次の分割では `alloc/string/utf8` または numeric parse/format を候補にする。
