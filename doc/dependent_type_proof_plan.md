# NEPLg2: 依存型・形式証明への拡張構想（Draft）

最終更新: 2026-03-15

## 1. 目的

本ドキュメントは、NEPLg2 の現在進行中のリブート（`purity_ownership_memory_spec.md` などのメモリ安全性モデル実装）を土台として、最終目標である**「強力な静的・型検査・所有権システム・完全な検証、および依存型（Dependent Types）による形式証明」**へと接続するための未来の仕様構想（青写真）を記述する。

現在実装中の Pure Persistent / Unique Mutable / Linear Capability の安全モデルは、本構想を実現するための完璧な Prerequisite（必須要件）として設計されており、アーキテクチャの大規模な破壊なしに自然な拡張として形式証明の世界を導入できることを示す。

## 2. 実現のための三大追加要素

依存型と形式証明を導入するため、現在の静的解析基盤の上に以下の機能を追加する。

### 2.1. コンパイル時関数評価 (CTFE: Compile-Time Function Evaluation)

依存型では、型シグネチャの一部として任意の値（式）が出現する（例: 長さ `n+1` の配列を要求する関数）。これをコンパイル時に解決するため、コンパイラ内に `Pure` 関数を安全に実行できるインタプリタ（CTFE エンジン）を設ける。

- **現在の土台**: NEPLg2 は副作用（`ExternalIO` 等）と純粋関数（`Pure`）を厳格に分離している。
- **拡張内容**:
  - コンパイラ（型チェッカ）は、型文脈に出現した式が `Pure` であるかを検証する。
  - `Pure` な HIR（High-Level IR）に対し、コンパイラ内部で直接評価回し（Reduction）を行う。
  - Escape Analysis によって表面上 `Pure` と見なされた内部の生メモリ操作（`InternalAlloc`）も、コンパイラ内の安全なサンドボックス（インタプリタ）上で模倣実行し、最終的な純粋な値（`Pure Persistent`）として確定させる。数学的な純粋性とアルゴリズムの実行効率（ミューテーション）を両立したまま、型を評価する。

### 2.2. 全域性・停止性チェック (Totality / Termination Checking)

型を検査する過程で CTFE エンジンが無限ループに陥らないようにするため、「コンパイル時に実行されるコードは必ず停止する」ことを静的に保証するチェッカを導入する。

- **現在の土台**: NEPLg2 は式指向であり、強力な字句解析・文法・モジュール解決を備えている。
- **拡張内容**:
  - `Pure` 関数に対し、明示的または暗黙的に Totality Check パスを追加する。
  - ループ（`while`）内の変数が単調に停止条件へ向かっているか（Variant 定理）、再帰関数において引数が構造的に小さくなっているか（Structural Recursion）を静的に解析する。
  - ※ 停止しない（部分）純粋関数は `Partial` など別のアノテーションで区別し、型レベル（CTFE）での評価を拒否する。

### 2.3. 命題と同値性 (Propositional Equality & Proof Objects)

数学的な証明（例: `A + B = B + A`）をプログラムの型として表現し持ち回るための、証明オブジェクト（型）を導入する。

- **現在の土台**: `Diag.kind` 等による構造化された識別子や、構造的型同値による `trait` システムなど、型レベルの厳密な同値判定基盤が存在する。
- **拡張内容**:
  - `Eq<A, B>` のような「型 `A` と型 `B` が等しいことの証明（命題型）」を言語機能として組み込む。（Martin-Löf の等価性などに基づく）
  - プログラマは、コンパイル時に検証可能な同値性証明関数の戻り値として `Eq` のインスタンスを構築し、それを「通行手形」として安全なAPIに渡す。
  - これにより、配列の境界外アクセスのような実行時チェックが不要な、「インデックスが常に境界内にあることの静的証明」を引数に要求することができるようになる。

## 3. 現在のメモリ安全モデルとの完璧な接続

現在の NEPLg2 リボン計画が、どのように依存型へシームレスに繋がるのかの理論的根拠：

- **参照の不変性（Immutability）**:
  依存型において最も恐ろしいのは、「型レベルで評価に用いた値が、別の参照（エイリアス）から破壊的変更を受けること」である。
  NEPLg2 では、**ValueCategory（純粋永続 / 一意可変 / 線形）** によって、型レベルで利用してよい値を `Pure Persistent` に限定できる。永続で不変な値しか型パラメータに入らないため、証明が実行時に崩れることはない。

- **確定的なスコープと寿命（No GC）**:
  GC による非決定的なメモリ解放はシステムの挙動予測を難しくする。NEPLg2 が備える **Region Inference**（Pure 値の自動スコープ解法）と **Drop Elaboration**（所有権に基づく自動 Drop）は、コンパイラが「どこで確保し、どこで解放されるか」の厳密な証明パスを内包していることを意味する。形式証明に不確実な（証明不能な）GC 挙動を持ち込まないという点で理想的。

## 4. 目指すべき依存型プログラミングコードの未来像 (Syntax Sketch)

以下は、NEPLg2 の前置記法を活かしたまま、未来に依存型を用いたプログラミングがどのように書かれるかのイメージである。
（※ 構文や仕様は変更される余地がある）

```neplg2
// : 型レベルで長さを追跡する Vector
let Vec struct .T .len:
    ...

// : 長さ N の Vector への push は必ず長さ N+1 の Vector を返す
let push .T .n %fn Vec .T .n .T -> Vec .T {n + 1} (list, item):
    // ...

// : 安全な要素アクセス。index が確実に 0 以上 len 未満であることの証明 (Proof) を型で要求する
// : 注釈内の `{}` は CTFE によりコンパイル時評価される。
let get .T .len .idx %fn Vec .T .len .idx -> Option .T (list, index)
  // idx が合法であることの証明型を仮想的な constraint として要求
  where %IsLess .idx .len:
    // ... インデックス境界チェックの assert 等なしで生メモリのオフセットアクセスが可能になる
```

## 5. ロードマップにおける位置づけと展開

1.  **Phase 0-6 (現在進行中)**:
    - `InternalAlloc` や `ExternalIO` 等の副作用分離、ポインタの隠蔽と `MemPtr` 化、Region / Resource IR・借用チェッカーによる GC レスのメモリ安全モデル確立。
2.  **Phase 7 (基盤完了後)**:
    - パフォーマンス・チューニングと言語エコシステムの安定化。
3.  **Phase 8 (依存型パラダイムへの昇華: 本構想の着手)**:
    - **CTFE の導入**: `Pure` な関数をコンパイラで実行できるようにする。
    - **Totality Checker の実装**: `while` や再帰の停止性を保証する。
    - **型の依存化**: `.T` などの型引数として、純粋な式 `{expr}` を渡せるように構文と型チェッカを拡張。
    - **Proof Objects**: `Eq` に代表される命題型を提供。
4.  **Phase 9**:
    - 標準ライブラリの一部（例: `Vec`, `List`, `str` の indexing）を、ランタイムパニックを発生させない「静的証明必須の究極の Safe API」へ格上げする。

## 6. まとめ

本構想は、「実行性能を引き出す低水準のメモリ制御／ミュータブル操作」と、「型システムが要求する厳密な純粋性」を、コンパイラがサンドボックス内の Escape Analysis を通じてシームレスに行き来できるようにする NEPLg2 の強力なアーキテクチャへの自信に裏付けられている。
現在のリブート計画の延長線上には、間違いなくこの「汎用言語の記述力を持った実用的な定理証明支援プログラミング環境」が接続される。
